## Summary

Recently, I improved the performance of [pgdog](https://github.com/pgdogdev/pgdog), a Rust-based connection pooler, load balancer, and sharder for PostgreSQL.

The [PR](https://github.com/pgdogdev/pgdog/pull/1360) for this optimization can be found here.

This resulted in an almost **8% performance gain** in the connection pooler.

## Finding the Issue

While exploring opportunities to optimize the connection pooler, I started by generating some flamegraphs. I ran a simple `SELECT` statement workload using `pgbench` and recorded the run using `samply`.

![Samply screenshot showing memcpy in Pool::get](https://i.ibb.co/zhd65fW7/Screenshot-from-2026-09-01-21-54-56.png)

As we can see, there is a `_memcpy_avx_unaligned_erms` call after the `Pool::get` function.

`Pool::get` does nothing but attempt to get a connection from the pool within a given duration and return a connection on success.

So what triggers this `memcpy`? Is it required? Can we avoid it?

## Debunking the Cause

The earlier flamegraph was generated from a release build, which did not provide enough symbol information to identify exactly which function was responsible for the `memcpy`.

I therefore generated another profile with better symbol information.

![Samply screenshot showing symbol information for the function causing memcpy](https://i.ibb.co/qF3YF9ff/Screenshot-from-2026-09-02-03-50-24.png)

The flamegraph made it evident that the `safe_timeout` function was responsible for the `memcpy`.

But why?

## `safe_timeout`

Looking at the implementation, the function is quite simple:

```rust
pub(crate) async fn safe_timeout<F>(
    duration: Duration,
    future: F,
) -> Result<F::Output, tokio::time::error::Elapsed>
where
    F: Future,
{
    tokio::time::timeout(duration, future).await
}
```

The function takes only two arguments: a `Duration` and a future. It then waits on `tokio::time::timeout` for the future to complete.

So what causes the compiler to generate a `memcpy` instead of simply performing a cheap move or inline copy?

Initially, I suspected that the `Duration` was too small to be responsible for such a large copy. This led me to look more closely at the future being passed to `safe_timeout`.

That eventually led me down the rabbit hole of Rust futures.

## Rust Futures

A Rust `Future` is a trait representing a value that may not be available yet. At its core, it exposes an associated `Output` type and a `poll` method.

The executor repeatedly polls the future until it returns either `Poll::Pending` or `Poll::Ready`.

The `Context` passed to `poll` also provides access to the task's `Waker`, which allows the future to arrange for itself to be polled again when progress can be made.

The [Rust Async Book](https://rust-lang.github.io/async-book/02_execution/02_future.html) is a great resource for understanding this in more detail.

## Async Functions in Rust

The `async` keyword provides a convenient way to construct a future without manually implementing the `Future` trait.

For example:

```rust
async fn add(a: i32, b: i32) -> i32 {
    a + b
}
```

Conceptually, the compiler transforms this into a state machine. A simplified representation might look something like:

```rust
enum AddStateMachine {
    Unresumed {
        a: i32,
        b: i32,
    },
    Returned,
    // ... other states generated by rustc
}
```

The exact generated representation is an implementation detail of the compiler, but the important idea is that an `async fn` produces a future containing the state required to resume execution.

A future can therefore be thought of as a state machine that moves through states such as "not started", "waiting", and "completed".

This is explained beautifully in [Understanding Async/Await in Rust](https://www.eventhelix.com/rust/rust-to-assembly-async-await/).

## Nested Futures

Now let's look at our `safe_timeout` function.

It is itself an `async fn`, and it awaits another future: the future returned by `tokio::time::timeout`.

Conceptually, we can think of its generated state machine as something along the lines of:

```rust
enum SafeTimeoutFuture<F: Future> {
    Unresumed {
        duration: Duration,
        future: F,
    },
    SuspendedAtTimeout {
        timeout: Timeout<F>,
    },
    Returned,
}
```

Again, this is only a conceptual representation of what the compiler generates.

The interesting part is that the future `F` initially exists as part of the `Unresumed` state. Once we construct the `Timeout<F>` future and start awaiting it, `F` becomes part of that `Timeout<F>` value.

This can require moving the future from one representation into another. If `F` is large enough, LLVM may lower that move into a call to `memcpy`.

This is the `memcpy` that showed up in the flamegraph.

This exact class of problem has also been discussed in:

- [Debloat your async Rust](https://tweedegolf.nl/en/blog/235/debloat-your-async-rust/)
- [The Size of Rust Futures](https://swatinem.de/blog/future-size/)

Both are excellent resources for understanding why seemingly small async functions can result in surprisingly large future types.

## The Solution

So, how do we avoid the expensive future copy?

The solution was surprisingly simple: I converted `safe_timeout` from an `async fn` into a regular synchronous function.

Instead of creating another async state machine around the timeout operation, the function directly returns the future produced by `tokio::time::timeout`.

This removes the additional layer of future nesting and, more importantly, eliminates the move of the large future that was showing up as `memcpy` in the profile.

The result was an almost **8% performance improvement** for the connection pooler under the benchmark workload.

## What About Boxing the Future?

Another possible solution is to box the future.

Instead of storing the entire future inline, a `Box` stores it on the heap and the surrounding future only needs to move a pointer. This can make moves of large futures significantly cheaper.

Boxing was also a natural choice for some other large futures in the codebase, and I eventually ended up boxing several of them.

However, boxing is not free.

It introduces a heap allocation and potentially adds an extra level of indirection. In my case, boxing all of the large futures also introduced other problems, which I will discuss in another blog post.

This was a good reminder that there is rarely a single "correct" optimization in systems programming. Different approaches have different trade-offs.

> In this case, the best optimization was not making the copy cheaper. It was removing the unnecessary future layer that caused the copy in the first place.
